Post-deployment verification · Open source · v0.1.0 pre-release

Green isn’t proof.

Your pipeline says success. AfterGreen checks whether the expected outcome actually happened.

01

A successful workflow is not a successful deployment.

A green pipeline confirms that the automation ran to completion. It says nothing about what users are now being served or what the database now contains.

What automation reports compared with what can still be true
The automation reportsWhat can still be true
deploy succeededThe application is still serving the previous version: a rollout that never switched traffic, a stale cache, the wrong target.
Endpoint returns 200The 200 comes from an old build or a maintenance page. A status code does not identify a release.
Database job completedThe row it was meant to write is missing or holds the wrong values.

AfterGreen does not read your pipeline’s status. It observes the outcome directly — the response at a URL, a row in a table — and compares it with what you expected.

02

Three verdicts. No implied success.

Every check ends in exactly one explicit verdict, printed as a word and returned as an exit code.

  1. VERIFIED

    exit 0

    The expected outcome was observed and every assertion holds.

  2. FAILED

    exit 1

    The outcome was observed and it contradicts what was expected.

  3. UNKNOWN

    exit 3

    The outcome could not be reliably observed: no response, a timeout, a truncated body.

UNKNOWN is never treated as success. If AfterGreen cannot see the outcome, it does not claim it. In the GitHub Action, UNKNOWN fails the step just as FAILED does.

03

How it works

  1. Deploy your application. However you deploy today. AfterGreen runs after it, from CI or a terminal.
  2. Define the expected outcome. For HTTP: a status code and text that only the new release serves, such as its commit SHA on a version endpoint.
  3. Run AfterGreen. One GET. Redirects are not followed. The body is read up to 1 MiB. No retries.
  4. Receive an explicit verdict. VERIFIED, FAILED or UNKNOWN, with the reason and a matching exit code your pipeline can act on.

Verify a deployment over HTTP

aftergreen http \
  --url https://app.example.com/version \
  --status 200 \
  --contains "$GIT_COMMIT_SHA" \
  --timeout 10s

Output when the old build is still live

FAILED  HTTP outcome (HTTP 200)
  - response body did not contain the expected text
$ echo $?
1

Install the CLI first, or run the same check from a workflow with the GitHub Action. Output never prints the URL, the response body or the expected text.

04

Install in one command.

Prebuilt binaries for Linux, macOS and Windows on amd64 and arm64. No Go toolchain, no root, no dependencies at run time.

macOS and Linux

Terminal

curl -fsSL https://aftergreen.foldnine.dev/install.sh | sh

The script detects your OS and CPU, downloads the release from GitHub, checks its SHA256 against the release’s SHA256SUMS and stops without installing anything if they differ. It installs to ~/.local/bin, never uses sudo and never edits your shell profile. Options: --bin-dir DIR, --version vX.Y.Z.

Homebrew (macOS and Linux)

brew install foldnine/tap/aftergreen

Or read the script before running it

curl -fsSLO https://aftergreen.foldnine.dev/install.sh
less install.sh
sh install.sh --bin-dir "$HOME/.local/bin"

Windows

PowerShell (amd64; use arm64 on Arm)

$v = "v0.1.0"; $a = "aftergreen_${v}_windows_amd64.zip"
$base = "https://github.com/foldnine/aftergreen/releases/download/$v"
Invoke-WebRequest "$base/$a" -OutFile $a
Invoke-WebRequest "$base/SHA256SUMS" -OutFile SHA256SUMS
$expected = ((Get-Content SHA256SUMS) | Where-Object { $_ -like "*  $a" }).Split(" ")[0]
if ((Get-FileHash $a -Algorithm SHA256).Hash.ToLower() -ne $expected) { throw "checksum mismatch" }
Expand-Archive $a -DestinationPath "$env:LOCALAPPDATA\aftergreen" -Force
& "$env:LOCALAPPDATA\aftergreen\aftergreen.exe" version

Add %LOCALAPPDATA%\aftergreen to your user PATH to run aftergreen from any directory.

Quick start

Your first verification

aftergreen http \
  --url https://example.com \
  --status 200 \
  --contains "Example Domain"

Output

VERIFIED  HTTP outcome (HTTP 200)
$ echo $?
0

Now expect a build that is not there

aftergreen http \
  --url https://example.com \
  --status 200 \
  --contains "a82f19c"

Output

FAILED  HTTP outcome (HTTP 200)
  - response body did not contain the expected text
$ echo $?
1

The page still answers 200, but the text you expected is not in it. For your own deploys, point --url at an endpoint that serves the build ID and pass that ID to --contains.

05

What exists today

AfterGreen is deliberately small. These are the checks in the v0.1.0 release; nothing on this page is planned work.

HTTP verification

aftergreen http

Checks the response status and, optionally, literal text in the body. Use a unique build ID so a stale release cannot pass.

CLI and GitHub Action

PostgreSQL verification

aftergreen postgres

Confirms that the row an automation claims to have written exists with the expected values. One read-only, parameterized SELECT that AfterGreen builds itself; it never runs SQL from configuration.

CLI only

Local evidence verification

aftergreen check

Evaluates a JSON evidence file of expected and actual values and returns a verdict per event. A demo and evaluation format.

CLI only

GitHub Actions integration

foldnine/aftergreen-action

Runs the HTTP check inside a workflow, with no dependencies and no token. Kept in step with the CLI by shared conformance tests.

HTTP checks only

Where each check runs
CheckGo CLIGitHub Action
HTTP status and body textYesYes
PostgreSQL row stateYesNo

Not built: other databases, workflow-tool integrations, a hosted service, a UI, retries or scheduling.

06

GitHub Actions deployment verification

Add one step after your deploy. The job only stays green if the deployed endpoint really serves the new build.

.github/workflows/deploy.yml

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      # ... your deploy steps ...
      - name: Verify the deployed build is live
        id: aftergreen
        uses: foldnine/aftergreen-action@v1.0.1
        with:
          url: https://app.example.com/version
          expected-status: '200'
          contains: ${{ github.sha }}
          timeout-seconds: '10'
Effect on the workflow
VerdictStep
VERIFIEDsucceeds
FAILEDfails the job
UNKNOWNfails the job
Invalid inputsfails, no verdict

Outputs verdict and observed-status are available to later steps. To react to a verdict instead of stopping, set continue-on-error: true and read steps.aftergreen.outputs.verdict.

v1.0.1 is an immutable release: the tag never moves. The v1 tag follows the latest v1.x.y if you prefer updates. For the strictest pinning, use the release’s full commit SHA.
